# Arbitrage Lab — инструкция по работе

Актуально для локальной версии от 18.10.2026. Папка проекта: `E:\informatica\кнопка деньги`. Интерфейс: **http://127.0.0.1:4317**.

## 1. Что делает программа

Приложение получает публичные котировки Polymarket и Limitless, сопоставляет бинарные рынки, рассчитывает доступную глубину, комиссии, стоимость двух сторон и предполагаемый результат. Заявки, баланс, переводы через Bybit и выплаты моделируются. Реальные ордера, кошельки и переводы не подключены; настоящие ключи не нужны.

В программе два независимых источника:

- **Реальные котировки** — публичные рыночные данные и виртуальные деньги.
- **Демо-сценарии** — синтетический рынок для проверки механики, отдельный баланс и история.

Запущенный сервер собирает котировки даже при выключенных виртуальных входах. Кнопка запуска виртуальной торговли управляет входами, а не самим сервером. После запуска/перезапуска новые входы находятся на паузе; открытые позиции и история сохраняются.

Предыдущие сессии из `D:\arbitrage`, состояние VPS и старые диагностические отчёты не переносились вместе с Git. Эта копия использует собственную папку `data/`.

## 2. Что установлено и требуется

- Windows, PowerShell, **Node.js 24.x** и npm. В PowerShell используйте `npm.cmd`.
- Интернет для публичных REST/WebSocket площадок.
- Microsoft Edge нужен только для автоматического браузерного теста. Для обычной работы подойдёт современный браузер.
- PostgreSQL, Docker и GPU для локального запуска не требуются.

Проверка версии:

```powershell
Set-Location -LiteralPath 'E:\informatica\кнопка деньги'
node --version
npm.cmd --version
```

Должна отображаться версия Node `v24...`. Зависимости и сборка уже подготовлены. После получения новой копии или изменения зависимостей выполните:

```powershell
npm.cmd ci
npm.cmd run check
npm.cmd run test:ui
```

`check` проверяет типы исходников и тестов, синтаксис интерфейса, запускает тесты и собирает `dist/`. `test:ui` запускает отдельный тестовый сервер на порту 4329, временные сессии и headless Edge. Скриншоты сохраняются в `data/mvp-desktop.png` и `data/mvp-mobile.png`.

## 3. Запуск, проверка и остановка

Откройте PowerShell и перейдите в папку проекта:

```powershell
Set-Location -LiteralPath 'E:\informatica\кнопка деньги'
```

Запуск в фоне:

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\scripts\start-local.ps1
```

Дождитесь сообщения `Local MVP started`, затем откройте http://127.0.0.1:4317. Скрипт проверяет Node 24, предотвращает повторный запуск записанного процесса и ожидает HTTP-проверку здоровья. Профилирование включается для запускаемого процесса, если переменная `EXECUTION_PROFILE` заранее не задана. Постоянные настройки PowerShell не изменяются.

Проверка состояния:

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\scripts\status-local.ps1
```

Скрипт показывает процесс, HTTP, паузу/работу входов, готовность каталога и подключения WS. При первом запуске сервер открывает UI раньше завершения поиска рынков. `HTTP healthy: True` и `Catalogue ready: False` в этот момент допустимы. Длительность загрузки зависит от площадок, пагинации и сети; число пар постоянно меняется.

Штатная остановка:

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\scripts\stop-local.ps1
```

Скрипт запрашивает завершение именно процесса этой копии и ждёт до 30 секунд. Если сетевые операции ещё заканчиваются, он сообщит об этом без принудительного завершения. Повторите проверку статуса. Для перезапуска сначала дождитесь остановки, затем выполните `start-local.ps1`.

Альтернативный запуск в текущем терминале:

```powershell
npm.cmd start
```

Терминал должен оставаться открытым; остановка — `Ctrl+C`. Не запускайте одновременно фоновый и терминальный варианты. Для просмотра профиля при таком запуске можно перед командой задать `$env:EXECUTION_PROFILE='true'`.

Автоматический запуск после перезагрузки Windows не настраивается. Режим сна и закрытие компьютера прерывают сбор котировок. Скрипты фонового управления рассчитаны на стандартный порт 4317; для другого порта используйте терминальный запуск и соответствующий URL.

## 4. Первая проверка интерфейса

По умолчанию включена **тёмная тема**. Кнопка в верхней панели переключает её на светлую; выбор сохраняется в этом браузере. Если открыта старая страница, обновите её через `Ctrl+F5`.

1. В верхнем переключателе выберите **«Демо-сценарии»**.
2. Выберите обычный сценарий и нажмите **«Запустить сценарий»**.
3. Примерно через 16 секунд проверьте сделку, комиссии, остатки и реализованный P&L. Сценарий задержанного расчёта занимает около 45 секунд.
4. В разделе **«Сделки»** откройте детали: стоимость при сигнале, повторную стоимость, цены сторон, возраст котировок и причины отказа.
5. Дополнительные сценарии показывают частичное исполнение, отказ, задержку выплаты и несовместимый расчёт. Их результаты не оценивают доходность рынка.
6. После проверки поставьте демо на паузу и вернитесь к **«Реальным котировкам»**.

## 5. Работа с реальными котировками и виртуальными деньгами

На странице загружается **не более 10 пар**, отсортированных по убыванию доходности после расходов. Поиск и вкладки применяются ко всей базе на сервере до выбора десятки. Вкладка **«По стратегии»** отбирает пары по установленному сроку удержания; остальные проверки входа продолжают действовать. В текущий рейтинг попадают только оценки с актуальными и согласованными стаканами. Если их меньше десяти, список короче; если их нет, показывается причина, а база продолжает обновляться.

Блок **«База обновляется в реальном времени»** показывает число сохранённых пар, свежих оценок, положительных оценок и время обновления. Каталог после перезапуска сначала доступен как сохранённые метаданные; котировки получают статус актуальных только после новых данных площадок. Число строк базы может временно превышать число вновь подтверждённых пар, пока полный обход каталога не завершён.

Рейтинг приходит отдельным потоком SSE примерно каждые **500 мс**; баланс и история обновляются отдельно. Это интервал доставки интерфейса, а не гарантия обновления каждой площадкой. Пауза симуляции не останавливает WS, обновление базы и рейтинга. Когда свежих положительных оценок нет, программа не должна создавать искусственные сделки. Отрицательный ROI означает расчётный убыток после расходов.

1. Дождитесь загрузки каталога и подключения обеих площадок. Смотрите полноту поиска и количество свежих рассчитанных пар.
2. В разделе **«Рынки и пары»** откройте условия интересующей пары.
3. Проверьте положительный исход, источник расчёта, период наблюдения/часовой пояс, порог и равенство, отмену/перенос и резервный расчёт. Похожее название не означает одинаковые выплаты.
4. После проверки всех пяти пунктов запишите обоснование и разрешите пару для виртуальных входов.
5. В параметрах стратегии выберите профиль, проверьте значения и сохраните их.
6. Нажмите кнопку запуска виртуальных входов. Дальше вход возможен только при подходящих котировках и прохождении проверок.
7. Контролируйте сделки, комиссии, остатки и реализованный результат. Пауза запрещает новые входы и отменяет ожидающие покупки; уже открытые позиции остаются в истории и продолжают обслуживаться.

Опция обхода ручной проверки предназначена для специальных paper-тестов. В обычном режиме оставляйте ручную проверку включённой. Поля раздела **«Подключения»** являются макетами и не подключают реальные счета.

**«Закрыть все сделки»** использует доступные bid и учитывает ликвидность/комиссии. Если ликвидности не хватает, позиция может остаться открытой. Это не равнозначно сбросу баланса или гарантированной продаже.

## 6. Основные настройки

Профили — исходные параметры, а не доказанный оптимум:

| Параметр | Профиль $200 | Профиль $500 |
| --- | ---: | ---: |
| Виртуальные средства на площадку | $100 | $250 |
| Целевые чистые контракты на сторону | 10 | 25 |
| Максимальная стоимость сделки | $10 | $25 |
| Общая экспозиция | $40 | $100 |
| Открытые позиции | 4 | 4 |
| Денежный резерв на площадку | $10 | $25 |
| Минимум ROI | 3% | 3% |
| Минимальная прибыль | $0.15 | $0.35 |
| Максимальный аварийный убыток стороны | $0.75 | $1.50 |
| Стоп по реализованному убытку | $6 | $15 |

Общее: модельная задержка **400 мс**, ожидание подтверждающего снимка до 1500 мс, допуск стоимости всей пары 0,5%, вероятность отказа 1% и частичного исполнения 3% как допущения модели. Автобалансировка по умолчанию выключена. Действующие пользовательские настройки видны в интерфейсе; повторно выбирать профиль при каждом запуске не требуется.

Новые попытки повторно проверяют общий бюджет обеих сторон: удорожание одной стороны может компенсироваться удешевлением другой. Проверки прибыли, глубины, резервов, риска и свежести сохраняются. Старые записи без полей бюджета пары продолжают использовать прежние ограничения отдельных сторон.

Не уменьшайте задержку и не отключайте ограничения ради появления сделок. Нулевое число входов может быть корректным результатом проверки рыночных условий.

## 7. Скорость и диагностика

В **«Журнале событий»** есть **«Профиль задержек»**:

- `JSON → объект` — явный JSON.parse; Limitless декодирует JSON внутри Socket.IO, поэтому эта метрика не измеряет его внутренний декодер.
- `Разбор и нормализация` — применение сообщений к состоянию стакана.
- `Очередь потока` и `Очередь решения` — ожидание обработки.
- `Котировка → решение` — время от получения сообщения приложением до завершения оценки движком для подходящих обновлений.
- `Котировка → надёжное сохранение` — тот же путь с ожиданием завершения операции и записи журнала.
- `Журнал транзакций`, `Полный снимок состояния`, `Подготовка интерфейса` — отдельные расходы.
- `Ожидание HTTP-лимитера` и `HTTP RTT` — разные интервалы. RTT не является временем исполнения ордера.

При паузе счётчики торговых решений могут не расти, хотя WS продолжает работать. Времена вложенных этапов перекрываются: складывать их нельзя. Перцентили рассчитываются по последним 4096 измерениям этапа. Задержка event loop измеряется таймером с разрешением 10 мс; значения включают это разрешение.

Технические показатели доступны локально:

```powershell
npm.cmd run verify:local
Invoke-RestMethod 'http://127.0.0.1:4317/api/health' | ConvertTo-Json -Depth 6
Invoke-RestMethod 'http://127.0.0.1:4317/api/diagnostics/profile' | ConvertTo-Json -Depth 6
```

`verify:local` проверяет HTTP, источники, обе сессии и профиль, сохраняет краткий отчёт в `data/analysis/local-validation-latest.json`. Ключи и токен управления в отчёт не включаются.

У потоков в health есть текущая/максимальная очередь, возраст ожидающих сообщений, число обработанных сообщений, ошибки и переподключения. `connected` само по себе не доказывает свежесть каждой пары: смотрите также свежие расчёты и причины блокировки.

Воспроизводимый CPU-бенчмарк:

```powershell
npm.cmd run build
npm.cmd run benchmark:performance -- data/analysis/performance-manual.json
```

Для сравнения запускайте его при одинаковой нагрузке компьютера, желательно с остановленным приложением. Он использует синтетические данные, 200 прогревочных вызовов и не измеряет сеть/диск/реальные исполнения. Для публичного HTTP отдельно существует `npm.cmd run benchmark -- --samples 20`; этот замер обращается к площадкам.

При проверке 18.10 обработка полного Limitless-стакана ускорилась примерно в 1,8 раза, а шаг для одной изменившейся пары в feed из 1000 — примерно в 4,9 раза. Полный пересчёт всех 1000 изменившихся пар по медиане существенно не ускорился. Подробности и ограничения — [отчёт об изменениях](docs/performance-release-2026-10-18.md).

GPU не используется. Текущий путь получения, обновления и оценки котировок работает на CPU. Пакетные исследования на GPU требуют отдельного прототипа и сравнения полной задержки на конкретном оборудовании.

## 8. Данные и резервное копирование

Всё рабочее состояние хранится в `data/`, исключённом из Git:

| Путь | Содержание |
| --- | --- |
| `paper-live/` | Сессия виртуальной торговли на реальных котировках |
| `paper-demo/` | Независимая синтетическая сессия |
| `paper-*/state.json` | Последний полный checkpoint |
| `paper-*/transactions.jsonl` | Надёжный журнал последующих транзакций |
| `paper-*/transactions-archive/` | Завершённые сегменты журнала |
| `paper-*/sessions/` | Архивированные сессии |
| `paper-reviews.json` | Ручные одобрения пар |
| `markets.sqlite`, `markets.sqlite-wal`, `markets.sqlite-shm` | Обновляемая база последних оценок и метаданных пар; вспомогательные файлы SQLite |
| `audit/` | Сжатые торговые события, настройки и критические ошибки |
| `diagnostics/` | Специальные отчёты/архивы, если сбор или доставка настроены отдельно |
| `observer.stdout.log`, `observer.stderr.log` | Вывод локального сервера |

Сначала транзакция записывается и сбрасывается на диск, затем операция считается сохранённой. Полный checkpoint создаётся периодически и при штатной остановке. Поэтому `state.json` может отставать от журнала; при следующем запуске более новые транзакции восстанавливаются автоматически. Неполный последний JSON-хвост сохраняется отдельно и ремонтируется; разрыв последовательности вызывает ошибку, а не молчаливую потерю средств.

Формат журнала поддерживает прежние полные записи и новые компактные записи **schemaVersion=2**. Старый код, не умеющий читать v2, нельзя просто запустить поверх новых данных. Перед откатом необходима совместимая версия чтения/экспорта и отдельная проверка копии; историю не заменять старым снимком.

`markets.sqlite` хранит последнюю оценку каждой пары без бесконечного архива тиков. Работа с SQLite вынесена в отдельный worker; изменения объединяются перед записью раз в 500 мс. Это восстанавливаемый кэш котировок; финансовая история по-прежнему хранится отдельно в `paper-*/`. Для полной копии SQLite штатно остановите сервер и копируйте каталог `data/` целиком вместе с вспомогательными файлами. Предупреждение Node 24 `SQLite is an experimental feature` само по себе не означает ошибку базы.

Для резервной копии штатно остановите приложение и убедитесь по статусу, что процесс завершился. Затем:

```powershell
Set-Location -LiteralPath 'E:\informatica\кнопка деньги'
$backupDirectory = Join-Path (Get-Location) 'backups'
New-Item -ItemType Directory -Path $backupDirectory -Force | Out-Null
$backupFile = Join-Path $backupDirectory ('arbitrage-data-' + (Get-Date -Format 'yyyyMMdd-HHmmss') + '.zip')
Compress-Archive -LiteralPath .\data, .\config -DestinationPath $backupFile
```

Храните копию отдельно от рабочей папки. Для восстановления остановите приложение и сначала сохраните текущую `data/` отдельной копией. Распаковывайте резервную копию в отдельную папку для проверки перед заменой рабочего состояния. Экспорт JSON/CSV в UI удобен для анализа, но не заменяет копию журналов и одобрений.

`reset:local` выполняет отдельный полный сброс с архивированием. Для запуска, исправления сети или обновления версии он не нужен.

## 9. Обновление программы

1. Остановите приложение штатно и сделайте резервную копию данных.
2. Проверьте `git status`. Текущие изменения кода локальные; не применяйте команды удаления/сброса поверх них.
3. После согласованного обновления исходников выполните `npm.cmd ci`, `npm.cmd run check`, `npm.cmd run test:ui`.
4. Запустите сервер и проверьте ID сессий, историю, балансы, параметры и паузу входов.
5. Включайте виртуальные входы отдельно после проверки состояния.

## 10. Если что-то не работает

**Страница не открывается.** Выполните `status-local.ps1`; проверьте Node 24 и наличие `dist/server.js`. Если сборки нет — `npm.cmd ci`, затем `npm.cmd run check`. Посмотрите последние строки `data/observer.stderr.log`.

**Порт 4317 занят.** Возможно, работает другая копия. Узнайте её папку и сохраните её данные. Не завершайте все процессы Node и не запускайте вторую копию поверх той же `data/`.

**Каталог загружается долго.** Проверьте `feed.phase`, `catalogError`, полноту поиска и сеть. Глобальный обход Polymarket может ещё идти, когда связанные пары уже доступны. Программа повторяет временные сетевые ошибки и соблюдает Retry-After.

**WS переподключается.** После сетевого обрыва стаканы соответствующей группы инвалидируются и запрашиваются заново. При сбросе версии издателя Limitless также выполняется восстановление через переподключение. Дождитесь свежих стаканов, затем проверьте ошибки и очередь.

**Слишком много HTTP 429.** Увеличьте `MIN_HTTP_INTERVAL_MS` для следующего запуска, например до 200–500 мс. По умолчанию между началами запросов к одному origin выдерживается 100 мс; это ограничение клиента, а не обещанная квота площадки. Срочное обновление для исполнения имеет приоритет перед каталогом, но не обходит cooldown.

**Положительный спред есть, входа нет.** Откройте причины у пары: ручное одобрение, свежесть, рассогласование времени, глубина покупки/выхода, минимальная прибыль, резерв, экспозиция, пауза и срок рынка. Спред до расходов недостаточен.

**Есть сигнал, затем отмена.** В деталях сделки сравните исходную и повторную стоимость, лимиты, возраст данных и причину отказа. Исчезновение возможности до прихода заявки — допустимый исход симуляции.

**Диагностика исполнения отсутствует.** В этой копии нет старого отчёта/SSH-конфигурации с другого компьютера. Основное приложение работает без них. Специальный сборщик и доставка описаны в `docs/execution-diagnostics.md`; они не запускаются автоматически без соответствующей конфигурации.

**Ошибка сохранения или предел архива.** Поставьте входы на паузу, остановите приложение, проверьте свободное место и сделайте копию `data/`. Не удаляйте WAL или непокрытые позиции ради возобновления работы. Обычные журналы не содержат непрерывного raw-потока котировок; большой специальный диагностический сбор должен иметь отдельные лимиты.
