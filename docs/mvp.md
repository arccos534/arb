# MVP v0.2: интерфейс и виртуальный счёт

Приложение работает локально по адресу **http://127.0.0.1:4317**. В этой версии нет механизма подписания реальных заявок или выводов. Режим реальной торговли отсутствует и не включается вводом ключей.

## Запуск

Из PowerShell в `D:\arbitrage`:

```powershell
npm.cmd ci
npm.cmd run check
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\scripts\start-local.ps1
```

Открыть http://127.0.0.1:4317 в браузере. Альтернатива в текущем терминале: `npm.cmd start`; остановка Ctrl+C. Для разработки: `npm.cmd run app`.

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\scripts\status-local.ps1
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\scripts\stop-local.ps1
```

Старый `observe` доступен для самостоятельного сканирования без UI. Не запускать его одновременно с MVP на одном `DATA_DIR`: MVP уже включает свой сканер. После перезапуска запись данных и расчёт существующих позиций возобновляются, но новые входы всегда поставлены на паузу.

## Два изолированных счёта

В верхнем переключателе:

- **Реальные котировки** — публичные рынки и стаканы Polymarket/Limitless, виртуальное исполнение и отдельный баланс. На старте по $100 на площадку. Нет проверенных выгодных пар — нет сделок.
- **Демо-сценарии** — отдельные синтетические данные, отдельный виртуальный капитал и P&L. Предназначены для проверки механики, а не для оценки доходности рынка.

Баланс, сделки, переводы, события и настройки этих счётов не смешиваются. На странице «Обзор» доступны капитал, реализованный и нереализованный P&L, график, средства по площадкам, пары и последние события.

## Проверка полного цикла за минуту

1. Выбрать «Демо-сценарии».
2. Выбрать «Полный цикл» и нажать «Запустить сценарий».
3. Увидеть резервирование средств, исполнение двух заявок с задержкой, открытую позицию и ожидание результата.
4. Примерно через 16 секунд обе площадки отдельно рассчитываются, появляется реализованный P&L.
5. В «Сделках» открыть детали: валовые/чистые контракты, комиссии, расход, остаток, выплаты, время и события.
6. Проверить сценарии отказа второй стороны, частичного исполнения, задержки расчёта (45 секунд) и несовместимых исходов. При отказе/частичном исполнении используется аварийная продажа по bid; при отсутствии bid экспозиция остаётся открытой.
7. После расчёта можно выполнить виртуальную балансировку через Bybit на странице «Сделки». Деньги проходят этапы депозита и вывода; в транзите они продолжают учитываться в капитале, комиссия списывается один раз.

Каждый новый сценарий создаёт новый синтетический рынок. До завершения текущего сценария следующий не запускается. При достаточном убытке действует тот же лимит потерь, что и на виртуальном счёте реальных котировок. «Новая сессия» сохраняет предыдущую в архиве и доступна после закрытия позиций и завершения переводов.

## Работа на реальных котировках

1. Дождаться каталога; первичная загрузка может занять около минуты и больше при тайм-аутах.
2. В «Рынках и парах» открыть «Правила». Проверить текст, источник, время, порог/равенство и отмену/резервный расчёт обеих площадок.
3. Поставить пять отметок только при совместимости, записать обоснование. Запись разрешает **только виртуальную торговлю** и привязана к хешам правил и сроку действия.
4. На обзоре запустить симуляцию. Вход возможен при поддержанной комиссии, свежих согласованных стаканах, достаточной глубине, соблюдении бюджета/резерва и доходности.
5. После сигнала резервируются средства двух площадок. Исполнение проверяется после заданной задержки по снимку, полученному **не раньше** предполагаемого поступления заявки. Старый снимок не используется как подтверждение исполнения.
6. Учитываются отказы и частичные FAK-исполнения из модели; их вероятности и seed доступны в параметрах. При несовпадении количества контрактов выполняется аварийный выход.
7. При завершении события деньги не зачисляются автоматически по таймеру. Каждая площадка опрашивается публично. Нужен явно окончательный результат; неподдержанный/спорный статус остаётся в ожидании.

В момент запуска нет одобренных рыночных пар. Положительные отображаемые оценки не являются доходом и не гарантируют сделку. По умолчанию `MAX_PAGES=0`, `MAX_WATCH_PAIRS=0`, `HORIZON_HOURS=0`, `MIN_HOURS_TO_END=0`: ноль снимает лимиты страниц, количества пар и максимального срока; уже завершившиеся рынки исключаются. Положительные значения этих параметров позволяют явно ограничить охват; интерфейс не выдаёт ограниченный каталог за полный.

В поток включаются все найденные пары; запросы стаканов дедуплицируются по площадке и рынку. Открытые позиции сохраняют подписки, проверенные пары имеют приоритет. Сначала публикуются пары с явной связью площадок, затем идёт полный обход Polymarket. Интерфейс показывает прогресс страниц и записей, полноту каталогов, причины отсутствия второго контракта, общее число пар, подписок и рассчитанных оценок. Полнота каталога не означает свежесть всех стаканов или прибыльность. Для строки без процента выводится причина: стакан не получен, недостаточная глубина, неизвестная комиссия и т. п. Количество строк — число пар-кандидатов, не совершённых сделок. Именованные бинарные исходы, например участники UFC, сохраняются в нормализации, но требуют отдельной ручной проверки соответствия сторон. Drift/Hedgehog пока не имеют подключённых исполнимых котировок.

Большие WebSocket-подписки разбиваются на группы максимум по 100 рынков с разнесённым стартом; ни одна найденная пара не отбрасывается из-за размера группы. REST-проверка по очереди обновляет устаревшие/отсутствующие стаканы, максимум 20 рынков за цикл, чтобы не превышать частоту запросов площадки; это ограничение темпа, а не общего списка наблюдения. Запросы на момент исполнения имеют отдельное подтверждение. Временные GET-ошибки повторяются до двух раз; HTTP 429 учитывает Retry-After. При неполном/неудавшемся полном обходе уже найденные пары продолжают получать котировки, а полнота в интерфейсе остаётся false.

Архив аудита сохраняет отдельные gzip-элементы для каждой записи, объединяя их в пакетные файловые записи. Предел очереди — 128 МБ; при его превышении или достижении лимита диска новые входы останавливаются с явной ошибкой. Перезапуск после сбоя очереди восстанавливает диагностику, но не запускает торговлю автоматически.

В параметрах стратегии есть флаг «Отключить ручную проверку пар — только виртуальная торговля» (`skipManualReview`, по умолчанию выключен). Перед изменением параметров нужно приостановить торговлю и завершить открытые позиции. Флаг пропускает проверку эквивалентности исходов при сигнале и виртуальном исполнении, но не меняет сохранённые ручные одобрения. Стаканы, комиссия, глубина, минимальная доходность, положительная прибыль, бюджеты, свежесть, срок рынка и неизменность правил между сигналом и исполнением продолжают проверяться. Для любого положительного процента установите минимальную доходность 0. Флаг и обход проверки фиксируются в настройках, заметках сделки и диагностике. Видимый плюс у непроверенных исходов не доказывает покрытие и может закончиться убытком.

На обзоре и странице пар есть также быстрый переключатель ручной проверки. Его можно менять во время симуляции; остальные настройки остаются заблокированными при открытых позициях. Режим сохраняется отдельно для live/demo и изменение записывается в журнал.

Пропуск ручной проверки не отменяет проверку идентичности: противоречащая ссылка Limitless на другой Polymarket market всегда блокирует расчёт и новые входы. Для непроверенных автоматических входов нужна совпадающая явная ссылка. После прихода заявки симулятор запрашивает новые REST-стаканы и ждёт подтверждения снимками, полученными после `executeAfter`, максимум `maxExecutionWaitMs` (1500 мс в профилях); отсутствие ценового изменения само по себе не означает немедленный отказ. Котировки после дедлайна не позволяют исполнить старый сигнал. Подробный разбор прежних ошибок и CSV: `docs/csv-analysis-2026-10-17.md`.

Перед первой виртуальной покупкой повторно проверяются обе стороны целиком: свежесть и согласованность времени стаканов, идентификаторы контрактов, полный чистый объём с комиссиями в исходных лимитах цен, минимальный размер заявки, резерв и доступный баланс. По этим же ограниченным стаканам заново рассчитываются общая стоимость, положительная прибыль и минимальная доходность стратегии с установленными буферами. Если хотя бы одна проверка не проходит, обе заявки получают `CANCELLED`, резервы освобождаются, списаний и комиссий нет. Устаревшие снимки по истечении ожидания также приводят к отмене всей попытки.

Один `execution-preflight` на попытку сохраняет причины, исходный и обновлённый расчёт, фактическую задержку, лучшие цены и расчёт каждой стороны. Потоки котировок не записываются. История событий хранит снимки объектов на момент события: последующее исполнение/закрытие не переписывает прежний статус заявки. Проверка перед отправкой не даёт атомарного исполнения между площадками: случайные отказы и частичные исполнения после успешной проверки продолжают моделироваться и могут потребовать аварийной продажи с убытком.

Пары и новые виртуальные входы упорядочиваются по проценту доходности после расходов по убыванию; неизвестные оценки находятся внизу таблицы. История сделок сортируется по сохранённому проценту при сигнале (`expectedRoi`), затем по времени. Старые сделки без сохранённого процента находятся внизу; результат при закрытии отображается отдельно.

В истории сделок заголовки столбцов переключают сортировку по событию, статусу, расходу, поступлениям, проценту при сигнале, реализованному P&L и времени входа. Повторный клик меняет направление; стрелка и aria-sort показывают текущий порядок. Неизвестные проценты остаются внизу при обоих направлениях.

Кнопка «Закрыть все сделки» на странице сделок относится к выбранному виртуальному счёту live/demo: запрашивает текущие стаканы, отменяет ожидающие заявки, приостанавливает новые входы и продаёт открытые позиции по доступной глубине bid с учётом комиссии. Итог показывает количество закрытых, отменённых и оставшихся позиций. Отсутствие котировок/ликвидности не обнуляет остаток и не создаёт фиктивную выплату. Повторный вызов пытается закрыть оставшееся; завершённая история сохраняется. После полного закрытия параметры доступны, если нет иных ограничений состояния.

## Как учитываются деньги

- Резерв под ещё не исполненную заявку уменьшает доступный баланс, но не списывает деньги со счёта.
- Виртуальная покупка списывает фактическую стоимость и денежную комиссию.
- Для Limitless ставка покупки (0,4–3% получаемых контрактов) и продажи (0,42–1,5% USDC) рассчитывается отдельно на каждом уровне стакана по опубликованной таблице: https://docs.limitless.exchange/user-guide/fees. Между точками применяется линейная интерполяция. Это оценка, не точная формула биржи: публичные данные не раскрывают её и персональную скидку. Валовой объём покупки увеличивается до целевого чистого покрытия; удержание округляется вверх до 6 знаков на каждом уровне. В диагностике сохраняются версия модели, цены, ставки и удержания. Рынки с явным metadata.fee=false считаются без комиссии, с отсутствующим флагом блокируются. Старые сохранённые заявки сохраняют исходную модель contracts-bound для воспроизводимости истории.
- Стоимость открытых позиций — ликвидационная оценка по свежим доступным bid с оценкой комиссии продажи. Недоступная или устаревшая ликвидность оценивается в ноль, поэтому график может резко снижаться даже у покрытой пары.
- Реализованный P&L появляется от продаж, подтверждённых выплат и комиссии виртуальной балансировки. Неиспользованный резерв расходов не списывается как фактическая комиссия.
- Суммировать положительные наблюдения нельзя. В сессии допускается один вход на конкретную пару/событие; количество одновременно занятых слотов ограничено, включая ожидание расчёта.
- Долларовая эквивалентность залога считается допущением. Риск pUSD/USDC и реальный маршрут конвертации пока не смоделированы.

## Подключения-заглушки

Для Polymarket, Limitless, Bybit и RPC подготовлены поля. Их значения остаются только в текущей форме браузера, не отправляются на сервер, не попадают в localStorage, экспорт или журналы и очищаются кнопкой «Проверить макет». Реальные ключи и приватные ключи сейчас не нужны. Эндпоинтов реального подключения, торговли и вывода нет.

## Подробные журналы

| Путь внутри `DATA_DIR` | Назначение |
| --- | --- |
| `audit/audit-YYYY-MM-DD-NNNN.jsonl.gz` | Торговые события, исполнения со стаканом, комиссии, расчёты, настройки и критические ошибки. Ротация сжатых файлов примерно по 16 МБ. Потоки REST/WS и снимки капитала не архивируются |
| `paper-live/state.json` | Текущее состояние виртуального счёта реальных котировок |
| `paper-demo/state.json` | Отдельное состояние синтетического счёта |
| `paper-*/transactions.jsonl` | Write-ahead журнал экономических изменений с последовательностью, событиями и полным следующим состоянием |
| `paper-*/sessions/UUID.json` | Архивы завершённых сессий после сброса |
| `paper-reviews.json` | Пользовательские проверки контрактов для paper trading |
| `observer.stdout.log`, `observer.stderr.log` | Вывод локального процесса |

Запись включает ID сессии/сделки/заявки, параметры модели, seed генератора, исходные и исполняющие стаканы, время сигнала/планового и фактического исполнения, комиссии в деньгах и контрактах, статусы, отказы, движения баланса и свидетельства расчёта. Публичные поля записываются полностью для подписанных рынков; данные неподписанных рынков не выдумываются и не реконструируются.

Торговый архив содержит последовательность gzip members; `gzip`, `zcat`, Node `gunzip` читают их последовательно. Интерфейс показывает последние торговые события и предоставляет загрузку архивов. «Экспорт сессии» содержит состояние JSON; CSV — сводку сделок. История UI ограничена для быстродействия; полные транзакции остаются в WAL/архиве. Частично записанный хвост WAL после сбоя сохраняется отдельно и восстанавливается без повторного списания.

В режиме MVP отключён дополнительный исторический журнал `events-*.jsonl` наблюдателя. Отчёты `*-latest.json` перезаписываются и не накапливают историю. Отдельные CLI-команды исследования сохраняют свой исследовательский журнал.

По умолчанию `AUDIT_MAX_MB=2048`. При заполнении или перегрузке очереди симулятор останавливает новые операции и сбор данных, показывает ошибку. Транзакционный WAL ограничен 256 МБ на счёт; для длительных исследований нужно архивирование. Старые файлы не удаляются автоматически. Логирование «без лимитов» быстро заполнит диск, особенно при полном WS-потоке.

## Проверки и границы MVP

`npm.cmd run check` выполняет типизацию, синтаксис интерфейса, тесты и сборку. `npm.cmd run test:ui` проверяет UI в headless Microsoft Edge, включая демо-выплату, P&L, детали, настройки, поля-заглушки, выгрузку логов и мобильную ширину. Тест использует отдельный временный каталог без реальных API и денег.

Это симуляция наблюдаемых снимков. Очередь maker, точный matching engine, рыночное воздействие виртуальных заявок, сетевые отказы блокчейна, индивидуальные лимиты/минимумы всех площадок, полный набор видов споров и реальная доступность средств вне приложения не воспроизводятся. Вероятности отказов/частичных fills — явные параметры, не результат измерения. Paper-прибыль требует последующей проверки минимальными реальными сделками при разрешённом доступе.

Сервер по умолчанию слушает только loopback, проверяет Host/Origin и локальный токен изменения состояния. Для будущего Docker-размещения предусмотрена публикация порта только на `127.0.0.1`; доступ с VPS планируется через SSH-туннель. Публичная публикация интерфейса требует отдельной аутентификации. Сейчас размещение на VPS не выполняется.
