# Диагностика исполнения

Сборщик запущен отдельно от торговой сессии. Он получает публичные стаканы,
создаёт независимые гипотетические сигналы и не исполняет заявки, не изменяет
баланс и не использует биржевые ключи.

## Текущий запуск

- VPS: имеющийся сервер в Нидерландах, 2 vCPU / 2 ГБ RAM.
- Служба: `arbitrage-diagnostics.service`, пользователь `arbdiag`.
- Начало: 17 октября 2026, 21:43:25 по Владивостоку.
- Окончание: 30 пригодных для анализа случаев либо 18 октября, 21:43:25.
- Код: `/opt/arbitrage-diagnostics/releases/20261017-v3` (17.10, пересчёт бюджета пары).
- Данные: `/opt/arbitrage-diagnostics/data`.
- Процесс ограничен 768 МБ RAM и 150% CPU, имеет пониженный приоритет.
- NTP переключён на доступный источник; `NTPSynchronized=yes` проверен.
  Конфигурация VPN, его порты и службы не менялись.

Профиль скопирован из текущих пользовательских настроек: 10 контрактов,
минимум $0.15, задержка основного режима 400 мс. Поскольку пользователь
включил обход ручной проверки, случаи помечаются `reviewed=false`.
Сборщик наблюдает соответствующие профилю пары со сроком до 24 часов;
отсутствие подходящих положительных сигналов не заменяется фиктивными сделками.

## Как смотреть

В локальном интерфейсе открыть **Журнал событий → Диагностика исполнения**.
Таблица содержит четыре задержки и две модели, число доступных,
недоступных и неопределённых случаев, а также расчётную сумму.

- JSON: `GET /api/diagnostics/execution`.
- CSV: `GET /api/diagnostics/execution?format=csv`.
- Локальная копия: `data/diagnostics/execution-latest.json`.
- Состояние доставки: `data/diagnostics/replication-status.json`.
- Доставка выполняется каждые 30 секунд; при отсутствии обновлений сводка
  помечается устаревшей. Доступ к VPS нужен только для получения отчёта.
- При старте `scripts/start-local.ps1` доставка запускается автоматически,
  если существует локальная конфигурация и нет уже работающего экземпляра.

SSH-ключ доставки отдельный. На сервере он разрешает только чтение отчёта,
без интерактивной оболочки и перенаправления портов. Пароль сервера в проекте
не сохраняется. Сборщик продолжает работу при выключенном локальном приложении;
после запуска приложения свежая сводка снова загружается с VPS.

## Что измеряется

Для каждого сигнала сохраняется окно −2 / +3 секунды. Длительность измеряется
монотонными часами; исходные UTC-метки площадок сохраняются отдельно.
Буфер ограничен 64 МиБ с учётом резерва на записи, архив — 256 МиБ.
В v2 лимит кадров одного случая увеличен с 2 до 8 МиБ: первые четыре
архива подтвердили обрезку по прежнему лимиту до конца нужного окна.
Причины incomplete сохраняются отдельно: case-byte-limit,
buffer-evicted, window-not-finished. Переполнение по-прежнему даёт unknown.
Сохраняются до 20 уровней каждой стороны; обрезка, переполнение, обрыв связи
и изменение часов не превращаются в успешные покупки.

При задержках 50/100/200/400 мс сравниваются одинаковые данные, исходные
лимиты, комиссии, объём и ограничения риска:

- `post-arrival`: первый набор новых пригодных снимков после прихода заявки,
  ожидание ограничено текущим `maxExecutionWaitMs`.
- `at-arrival`: последний полученный свежий стакан на момент прихода.
  Это оценка возможности, а не подтверждение сделки.

Вердикты `supported` и `possible` означают только поддержку модели
публичными наблюдениями. Настоящие исполнение, очередь заявок и будущая
эквивалентность выплат ими не подтверждаются. При нехватке записанной
глубины вердикт `unknown`. Непроверенные правила отражаются в JSON/CSV.

Суммы — сравнение **независимых сигналов**, а не прибыль портфеля:
общая ликвидность и капитал между разными случаями не переиспользуются
в качестве доказательства реализуемой совокупной доходности.

Сборщик сам завершается после достаточной выборки или лимита времени.
При нехватке пригодных случаев отчёт содержит `insufficientData=true`.
Основная стратегия, её задержка и финансовая история автоматически не меняются.

## Управление VPS

Проверка: `systemctl status arbitrage-diagnostics --no-pager`.
Остановка: `systemctl stop arbitrage-diagnostics`.
Повторный запуск службы продолжает текущую выборку с исходным пределом
времени. Для отдельного нового исследования нужна новая директория данных;
существующий архив сохраняется.

Проверки v3: `npm.cmd run check`, 151 тест и сборка, включая пересчёт
пары и совместимость с прежними лимитами, плотное
окно более 2 МиБ, причины обрезки, тихий стакан, уход цены, неполную глубину,
обрыв, рассинхронизацию, скачок часов, лимиты памяти/диска и восстановление
архива после сбоя; браузерная проверка таблицы и CSV, а также реальный
просмотр отчёта с VPS через локальный интерфейс. `npm.cmd run test:ui`
прошёл после добавления карточки проверки исполнения и счётчиков.

V1/v2 сохранены; drop-in `30-release-v3.conf` переключает сборщик на v3.
Данные остаются в прежнем каталоге. Копии службы, предыдущего drop-in,
отчёта и 12 архивов — `/opt/arbitrage-diagnostics/backups/20261017-v3`;
хеши и чтение gzip/JSON проверены. Для отката убрать только этот drop-in,
выполнить daemon-reload и перезапустить сборщик (возврат на v2).
Данные при откате не заменять старым снимком. Старые случаи остаются
в группе legacy-leg-limits, новые — pair-budget-v1; JSON/CSV/UI
позволяют смотреть их отдельно. [Модель исполнения](pair-budget-execution.md).
