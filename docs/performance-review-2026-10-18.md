# Разбор производительности — 18.10.2026

Задача: описать проект и определить приоритеты ускорения получения и обработки котировок. Исходный код в рамках разбора не менялся. Проверен коммит `55139d523f5aea79e8e2c86a40adf8db568b7c0b`, Node.js 24.14.0, Windows, папка `E:\informatica\кнопка деньги`.

## Устройство

Приложение исследует арбитраж Polymarket ↔ Limitless. Получает каталоги и правила, сопоставляет бинарные рынки, поддерживает стаканы через публичные WS/REST, рассчитывает глубину/комиссии/ROI и симулирует исполнение двумя виртуальными заявками. Результаты, риск, балансы и диагностика доступны в локальном UI. Реального исполнения нет.

Путь сообщения: `PublicStreams` → `StreamQueue` → `PolyStreamState` / `LimitlessStreamState` → `BookCache` → индекс затронутых пар в `ResearchRunner` → `DecisionScheduler` → `Application.tick` → `PaperEngine` → журнал/сохранение. На Polymarket `JSON.parse` выполняется до StreamQueue; Socket.IO самостоятельно декодирует сообщения Limitless.

Уже есть событийный запуск, объединение обновлений за 5 мс, адресная оценка пар, кэш оценок, ограниченная очередь с уступкой event loop, восстановление REST и защита от устаревших ответов. Интерфейс опрашивает `/api/state` раз в 2 с; это не частота получения котировок. Таймер 250 мс служит резервной проверкой. Задержка 400 мс относится к модели заявки.

## Измерения

Новые изолированные CPU-микробенчмарки: по 200 прогревочных вызовов; 2000 измерений на операцию парсера, 60–100 на вариант движка. Сырые агрегаты: `data/analysis/performance-review-2026-10-18.json`.

| Операция | p50, мс | p95, мс |
| --- | ---: | ---: |
| JSON.parse полного Poly-стакана, 20 asks + 20 bids | 0.0066 | 0.0098 |
| Poly полный стакан, 20+20: JSON + нормализация + cache | 0.0716 | 0.0999 |
| Poly одна дельта, 20 asks: JSON + применение + cache | 0.0025 | 0.0094 |
| Limitless полный стакан, 20+20: JSON + YES/NO + cache | 0.1715 | 0.3512 |
| Poly полный стакан, 100+100: JSON + нормализация + cache | 0.3730 | 0.5974 |
| Limitless полный стакан, 100+100: JSON + YES/NO + cache | 0.8345 | 1.0799 |
| PaperEngine: 1000 пар, неизменные стаканы, прогретый кэш | 7.2320 | 8.0305 |
| PaperEngine: 1000 пар, заменены все массивы уровней | 61.2415 | 66.7998 |
| PaperEngine: одна изменившаяся пара в feed из 1000 пар | 1.1128 | 1.5356 |

Это синтетические данные одной машины. Полные стаканы отсортированы, дельта изменяет существующий уровень. В варианте всех изменившихся пар таймер включает создание новых массивов уровней. В микробенчмарке Limitless JSON.parse включён для сопоставимости; в приложении декодирование выполняет Socket.IO. Ни один результат не включает сеть, ожидание очереди, файловую запись, нагрузку UI или реальное исполнение. Отличие 7 и 61 мс показывает чувствительность к кэшу, а не ускорение одного алгоритма относительно другого. Для реальных p95/p99 и пропускной способности нужен replay репрезентативного потока.

## Приоритеты

1. **Полные измерения пути получения → решения.** Сохранять монотонное время получения и измерять JSON decode, нормализацию, очередь, оценку, сохранение и полный путь отдельно. Сейчас метрика `decode` оборачивает `state.apply`, а JSON.parse находится раньше; `book-update` измеряет вставку в BookCache и callback. Добавить глубину/возраст очереди, задержку event loop, загрузку/GC и потерянное покрытие. Вложенные времена нельзя просто складывать. Для event loop доступен [monitorEventLoopDelay в Node 24](https://nodejs.org/docs/latest-v24.x/api/perf_hooks.html#perf_hooksmonitoreventloopdelayoptions).
2. **Убрать глобальную работу при локальном изменении.** `ResearchRunner.snapshot(false)` всё равно обходит наблюдаемые рынки; `PaperEngine.cache()` пересоздаёт обёртки всех стаканов. Дополнительные копии создаёт расчёт метрик. Сохранять общий доступный только для чтения индекс стаканов, передавать затронутые пары и отдельно создавать локальное представление потреблённой виртуальной ликвидности. Это сохраняет изоляцию симуляции от реального feed.
3. **Нормализовать и сортировать один раз.** `limitlessBooks()` дважды обрабатывает исходные уровни для YES/NO и сортирует четыре массива. Сначала разобрать YES, затем построить зеркальный NO с повторным использованием размеров и правильным порядком. `quoteBuy()` и `quoteSell()` снова сортируют уже нормализованные уровни. Прежде чем убрать сортировки, закрепить инвариант порядка на всех путях создания Book, включая тесты и демо; неожиданный порядок проверять/нормализовать. Сохранять точное округление, шаг цены и комиссии. Документация Limitless описывает [полные отсортированные снимки и микроконтракты](https://docs.limitless.exchange/developers/websocket/market-data).
4. **Разделить обработку котировок, подготовку UI и checkpoint.** `Application.view()` обходит все пары и выполняет оценки/проверки при каждом запросе; сериализация ответа также занимает основной JS-поток. Дать UI кэшированное представление с версиями и постраничной историей. `PaperRepository.commit()` записывает полное состояние в WAL и затем checkpoint; `DecisionScheduler` ждёт завершения решения вместе с сохранением. Рассмотреть компактные транзакции и менее частый checkpoint после надёжного WAL, сохранив восстановление и порядок финансовых операций. Потоки/процессы вводить по профилю нагрузки: [Node workers помогают CPU-работе, но мало помогают I/O](https://nodejs.org/docs/latest-v24.x/api/worker_threads.html).
5. **Сохранять действующие подписки.** В `publishDiscovery()` любое изменение состава/правил наблюдаемых рынков перезапускает PublicStreams целиком; группы заново запускаются с шагом 1 с. Обновлять только затронутые соединения, контролировать acknowledgement и получение начальных снимков. Для Limitless новая подписка заменяет предыдущую и выдаёт полный набор снимков — [это нужно учитывать при обновлении групп](https://docs.limitless.exchange/developers/websocket/market-data).
6. **Ускорять каталог отдельно от потока цен.** В Limitless после каждой страницы стоит пауза 1000 мс. Вместо произвольного снятия пауз нужен общий ограничитель запросов, ограниченный параллелизм независимых страниц, повторная сверка полноты и backoff по 429/Retry-After. Каталог не должен задерживать действующие подписки. [Limitless не публикует общую численную квоту](https://academy.limitless.exchange/academies/api_academy/09_RateLimits.html); пример настройки из документации не является гарантированным лимитом.
7. **Вторичные расходы.** Заменить Array.shift в StreamQueue на индекс головы/кольцевую очередь, уменьшить промежуточные массивы и повторный JSON.stringify постоянной части ключа EvaluationCache. Числа цены можно кэшировать или хранить в точном целочисленном масштабе после проверки диапазонов; финансовую арифметику и округления нельзя без проверки переводить на float. Последовательность дельт Polymarket сохранять.

Обработка рынка и глубокая диагностика имеют разные требования к полноте: пропуск промежуточных кадров может скрыть короткую возможность и изменить replay. Ускорение принимать по совпадению результатов на одинаковом потоке, p95/p99 полного пути и устойчивости к всплескам, а не по одному среднему времени JSON.parse.

## Подтверждённый риск свежести Limitless

`LimitlessStreamState.apply` отбрасывает `version <= previous`. [Документация площадки](https://docs.limitless.exchange/developers/websocket/market-data) допускает перезапуск счётчика после backend failover. В синтетическом сценарии после версии 100 и цены 0.6 пришла версия 1 с более новым timestamp и ценой 0.5: кэш сохранил 0.6, receivedAt не продвинулся. Если соединение не пересоздано, новые меньшие версии продолжают отбрасываться; проверки свежести впоследствии остановят использование такого стакана.

Нужен контролируемый resync при обнаруженном рестарте издателя или длительном отсутствии принятых обновлений: инвалидировать состояние, переподписаться/получить снимок, сверить время и восстановить последовательность. Безусловно принимать меньшие версии нельзя: это сломает защиту от сообщений не по порядку. REST-кэш может временно помочь приложению, но не исправляет версионное состояние WS.

## Порядок реализации

Сначала исправить восстановление после сброса версии и добавить сквозные измерения; затем убрать повторную нормализацию/сортировки и глобальное копирование. После замеров под нагрузкой отделить UI и checkpoint, улучшить обновление подписок и обход каталога. Для каждого изменения сравнить результаты на одинаковых сообщениях, затем выполнить `npm.cmd run check`; при изменениях UI — `npm.cmd run test:ui`.

Измерять сетевую доставку отдельно с предполагаемого рабочего хоста. Текущие микробенчмарки не позволяют заключить, что сеть или CPU являются главным ограничением в живом запуске. Модельную задержку 400 мс и ограничения риска в этом разборе не меняли.
